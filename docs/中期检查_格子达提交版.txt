二、已完成的主要工作
==================================================

2.1 后端架构与基础框架搭建

后端基于 Spring Boot 3.2 框架构建，采用经典的分层架构（Controller → Service → Repository），推荐引擎作为独立业务模块（service/recommendation 包）与普通业务逻辑解耦。具体完成工作包括：（1）设计并实现了五大核心数据表——用户表、歌曲表、歌单表、歌单-歌曲关联表、用户-歌曲交互记录表，全部使用 Spring Data JPA 进行数据持久化；（2）实现了双通道安全认证体系——Web 端采用 Spring Security 表单登录 + Session Cookie + CSRF 防护 + Kaptcha 验证码，小程序端通过独立的 JwtAuthFilter 过滤器从 Authorization Bearer 头解析 Token 并自动注入 Spring Security 上下文，两种客户端互不干扰；（3）配置层实现了全局异常处理（GlobalExceptionHandler）、Gzip 压缩、静态资源 7 天缓存、CORS 跨域支持等工程优化；（4）引入了 Python 种子数据脚本，生成了 555 首歌曲、130 个模拟用户、7393 条交互记录的完整演示数据集，涵盖 12 种音乐风格。

2.2 三种推荐算法实现

协同过滤模块（CollaborativeRecommender）同时实现了基于用户（UserCF）和基于物品（ItemCF）两种模式。相似度计算采用皮尔逊相关系数为主、Jaccard 相似度为辅的融合策略——当用户共同交互的歌曲数不足 2 首时自动退化为 Jaccard 计算，解决了稀疏数据场景下皮尔逊系数波动剧烈的问题。用户-物品交互矩阵将隐式反馈（点赞记 2 分、播放记 1 分）转换为偏好评分，避免了传统方法中"未交互 = 不喜欢"的假设陷阱。

内容推荐模块（ContentBasedRecommender）从歌曲的风格标签构建 one-hot 特征向量，对用户历史交互歌曲的特征向量求均值得到用户画像，再计算候选歌曲特征与用户画像的余弦相似度作为推荐得分。该模块独立于用户行为数据，在冷启动场景下能快速产生有一定准确度的推荐，是混合推荐引擎中不可或缺的兜底策略。

混合推荐模块（HybridRecommenderService）采用四路加权融合策略（协同过滤 + 内容推荐 + 热门推荐 + 探索多样性），并根据用户交互数据量实现了动态权重调整机制：当用户无交互记录时进入冷启动模式（热门 50% + 随机打散 50%），当用户交互稀少（≤5 条）时自动提高内容推荐权重至 50%、协同过滤降至 20%，当用户有充足行为数据（>5 条）时以协同过滤为主（50% 权重）、内容推荐为辅（20%）。

2.3 推荐质量评估模块

实现了完整的推荐质量离线评估模块（RecommendationEvaluator），采用业界标准的留出法（Hold-Out）划分训练集和测试集：对每个用户随机隐去 20% 的交互记录作为 ground truth，物理删除后调用推荐算法，再恢复交互记录，确保算法在计算时完全没有"偷看"答案。评估输出三个核心指标：Precision@K（推荐前 K 首中用户实际听过的比例，衡量精准度）、Recall@K（用户实际听过的歌中被推荐出来的比例，衡量覆盖面）、NDCG@K（考虑排序位置的归一化折损累积增益，衡量排序质量）。对 130 个模拟用户进行全量评估的结果显示，混合推荐在 Precision@5 上略低于纯内容推荐（0.318 vs 0.331），但在 Recall@10 上超过纯协同过滤（0.246 vs 0.253），整体表现最均衡。

2.4 Web 前端与播放器实现

Web 端采用 Thymeleaf 服务端渲染，通过 Fragment 机制将侧边栏、播放器、播放列表面板等组件模块化复用。配合 CSS 变量设计系统（深色主题）和原生 JavaScript 交互逻辑，实现了风格统一、交互流畅的用户界面。核心功能模块包括：（1）首页个性化推荐、热门歌曲、新歌上架、风格快捷入口；（2）完整的 Web Music Player 播放器——基于 HTML5 Audio API 的自定义实现，支持播放/暂停、进度条拖拽、循环模式切换、播放队列管理（可持久化到 localStorage）；（3）搜索功能——支持按歌名和歌手双向匹配；（4）歌单管理——创建/编辑/删除歌单、添加歌曲、公开/私有设置；（5）个人中心——用户基本信息、听歌统计、音乐风格偏好可视化。

2.5 微信小程序端与 REST API

REST Controller 层分为 MusicApiController（歌曲/搜索/歌单相关）、AuthApiController（登录注册）、AdminRecommendController（管理后台推荐接口）三类，统一输出 JSON 数据。路径前缀为 /api，在 SecurityConfig 中对 /api/** 关闭了 CSRF 校验。微信小程序端使用 WXML/WXSS/JS 原生框架开发，封装了 utils/request.js 统一处理鉴权、错误码解析和 loading 状态。已实现的核心功能包括：首页个性化推荐、热门歌曲、搜索、歌单浏览、登录注册（走 wx.login code2Session 换取后端 JWT Token）、歌曲详情页、点赞收藏。

2.6 推荐引擎管理后台

管理后台实现了完整的推荐引擎诊断页面（/admin/recommend），管理员可以：（1）查看全局统计数据——用户数、歌曲数、总播放量、各风格占比饼图；（2）对任意用户进行三种算法的单独诊断——查看每个算法分别推荐了什么歌、为什么推荐（相似度得分）；（3）一键触发全量离线评估——调用 /admin/api/recommend/evaluate 接口，等待约 154 秒即可得到 130 个用户的完整 Precision/Recall/NDCG 评估结果；（4）查看三种算法在该用户上的动态权重分配情况和用户阶段（冷启动/交互稀少/正常数据）。

三、遇到的问题及解决方法
==================================================


==================================================
问题 1：推荐链路中的 N+1 查询瓶颈
==================================================


==================================================
问题描述：在开发早期版本时，CollaborativeRecommender 的 batchLoadInteractions 方法在循环内反复调用 songRepository.findById()，一次推荐请求会产生数百条 SQL 查询，严重影响性能。
==================================================

解决方案：解决方案：在 Repository 层新增批量查询方法 findByIdIn(Collection<Long> ids) 和 findByUserIdIn(Collection<Long> userIds)，将循环内单条查询替换为批量 IN 查询 + Java 内存分组，SQL 数量从数百条降到个位数，推荐性能提升约 10 倍。同时修复了 Controller 层参数校验缺失的问题，对 page、limit 等参数统一使用 Math.max/min 做边界 clamp，避免前端误传参数时返回 500 错误。


==================================================
问题 2：Web 端与小程序端的双通道鉴权冲突
==================================================


==================================================
问题描述：设计初期只实现了简化的 Token 方案（固定字符串比对），Web 端和小程序端共用同一套鉴权逻辑。但 Spring Security 默认使用 Session Cookie，小程序无法传递 Cookie，直接关闭 CSRF 又会让 Web 端有安全风险。
==================================================

解决方案：解决方案：实现了完整的双通道鉴权体系。Web 端保持 Spring Security 原生的表单登录 + Session + CSRF + Kaptcha 验证码方案；小程序端独立实现 JwtAuthFilter（继承 OncePerRequestFilter），从 Authorization: Bearer xxx 请求头解析 Token，在内存 Map 中校验 TTL 过期时间后注入 Spring Security 上下文。SecurityConfig 中 .requestMatchers("/api/**").permitAll() + JwtAuthFilter 独立注册的方式，让两套机制互不干扰、按需生效。


==================================================
问题 3：种子数据不足导致协同过滤效果差
==================================================


==================================================
问题描述：初始种子数据只有 70 首歌、5 个用户、约 30 条交互记录，协同过滤在计算用户相似度时发现几乎没有共同交互的歌曲，皮尔逊相关系数波动剧烈甚至产生 NaN。
==================================================

解决方案：解决方案：重新编写了 Python 种子数据生成脚本（gen_seed_data.py + gen_interactions.py），采用分阶段策略生成 555 首歌曲、130 个模拟用户、7393 条交互记录。交互生成时模拟了真实的用户行为模式——"摇滚用户偏好摇滚"但偶尔也听流行，确保每个用户有足够的共同交互记录可供协同过滤计算。扩充数据后，协同过滤能找到有效邻居，推荐质量显著提升。


==================================================
问题 4：音乐播放器的触发事件绑定问题
==================================================


==================================================
问题描述：Web 端开发时遇到一个诡异的问题——点击歌曲卡片后播放器不触发，但直接在控制台调用 Player.play() 就能正常播放。排查了两个小时才发现，原因是 song-card 元素上没有 data-song 属性（Thymeleaf 的 th:data-song 渲染时 JSON 双引号被 HTML 转义）。
==================================================

解决方案：解决方案：检查模板渲染结果，确认 Thymeleaf 的 th:data-song="${song.toJson()}" 能正确生成 data-song 属性值，且 main.js 里的 document.querySelectorAll(".song-card") 选择器能匹配到首页上的 28 张歌曲卡片。此外还发现 main.js 使用 const Player 声明的全局变量不会挂到 window 上（JS 语言特性），所以在浏览器自动化测试中 typeof Player 只能返回 undefined，但在同脚本作用域里是正常工作的——这是测试方法问题，不是代码 bug。


==================================================
问题 5：管理后台 AdminController 的 principal 类型不匹配
==================================================


==================================================
问题描述：使用 JWT Token 访问 /admin/** 时，AdminController 的 @AuthenticationPrincipal org.springframework.security.core.userdetails.User（Spring 内置的 User 类）无法接收 JwtAuthFilter 注入的 com.music.recommendation.entity.User（我们的实体类），导致 currentUser 为 null 并返回 500 错误。
==================================================

解决方案：解决方案：将 AdminController 的参数类型改为 @AuthenticationPrincipal com.music.recommendation.entity.User admin，并增加 null 检查保护。同时新增了 /admin/dashboard 路由映射。修复后，Web Session 和小程序 JWT 两种方式都能正常访问管理后台。


==================================================
问题 6：评估模块的数据泄漏风险
==================================================


==================================================
问题描述：评估模块初始版本在内存中划分训练集/测试集，但推荐算法仍然会查询全量数据库，测试集中的交互可能被算法"偷看"。这种做法在学术上被称为数据泄漏，会导致评估结果虚高。
==================================================

解决方案：解决方案：将评估流程改为严格的"物理隔离"——随机隐去 20% 交互后，通过 Spring Data JPA 的 deleteAll() + flush() 物理删除这些交互，然后调用推荐算法，最后再 saveAll() 恢复。这样推荐算法计算时确实看不到测试集的交互记录，评估结果更可信。
