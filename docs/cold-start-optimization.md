# 冷启动场景算法优化方案

> **版本**: v1.0 | **日期**: 2026-10-02 | **Commit**: `71dc9b9`

---

## 1. 问题背景

### 1.1 冷启动定义

推荐系统的冷启动问题指新用户（0-3 次交互）或新物品缺乏数据导致推荐质量急剧下降。本项目中的混合推荐引擎基于五档自适应权重设计，其中冷启动档（原档 0，0-3 次交互）的权重分配为：

```yaml
# 旧版（凭直觉设计）
档0: cf=5%, cb=45%, popularity=30%, explore=20%
```

**核心假设**：CF 在冷启动下邻居少 → 给低权重；CB 不依赖交互 → 给高权重。

### 1.2 评估方法

真实冷启动用户在数据库中仅 4 人（1-3 次交互），统计上不足以支撑 Hold-Out 评估。因此设计**模拟冷启动评估**：

1. 从 48 个活跃用户（交互 ≥ 10）中取子集
2. 对每个用户**随机保留 3 条交互**做训练集（模拟新用户只有 3 次交互）
3. 其余 5 条（cap=5）作为 ground truth
4. 物理删除 ground truth 交互 → 调推荐 → 恢复交互 → 计算指标
5. **Ground truth cap=5 与老用户评估的 20% 留出（约 4-6 首）量级严格对齐**，保证两种场景指标可比

### 2.2 老用户评估（20% 留出，50 用户）

### 2.3 三项关键发现

#### 🔥 发现 1：ItemCF 对目标用户冷启动极其鲁棒

**传统认知**：CF 冷启动 = 邻居少 = 差。
**实际数据**：ItemCF 在冷启动下 N@10=0.553 甚至比老用户 0.511 **更高**！

**根因分析**：本项目 CF 实现是 **Item-Based 协同过滤**，核心是**物品间的共现余弦相似度**：
> "用户听过歌曲 A，而 A 和 B 被很多人同时听过 → 推荐 B"

这个过程只依赖 **歌曲本身的流行度和共现关系**，根本不依赖目标用户有多少邻居。**哪怕只有 1 首种子歌就能推荐**。

```
冷启动 (3条训练): ItemCF N@10 = 0.553 ✓ 远超 CB 0.442
老用户 (完整交互): ItemCF N@10 = 0.511
```

#### 💀 发现 2：ALS 矩阵分解在本数据集全面崩塌

ALS 在两种场景下 N@10 都只有 **≈0.13**，比 CF 差 4 倍！可能原因：

| 可能原因 | 分析 |
|---------|------|
| 数据集太小 | 仅 53 用户、~200 歌曲，隐因子模型严重欠定 |
| latentDim=8 度过高 | 对稀疏数据，高维度隐因子空间过拟合严重 |
| 闭式解数值不稳定 | 稀疏输入下 (PᵀP+λI) 条件数大，求解精度低 |
| 隐式评分设计问题 | `r = 0.1 + 0.9 × playCount/playMax` 可能不足以区分用户偏好 |

#### 🐛 发现 3：原 Hybrid 融合逻辑完全反了

```java
// 原代码（有 Bug）
double cfRatio = 0.60, alsRatio = 0.40;   // ALS 拿了 40% 权重！
if (cfSongs.size() < 3) {
    cfRatio = 0.30; alsRatio = 0.70;       // CF 空结果 → 向 ALS 倾斜？完全反了！
}
```

- ALS N@10 只有 0.13，40% 权重把 Hybrid 拖成渣（冷启动 N@10=0.482 甚至低于 CB 0.442）
- CF 空结果时还反向倾斜 ALS → 原假设"ALS 对稀疏更鲁棒"**在本数据集完全不成立**

## 3. 优化方案（数据驱动）

### 3.1 改动 A：Hybrid CF:ALS 权重重配

| 场景 | 旧值 CF:ALS | **新值 CF:ALS** | 理由 |
|------|:-----------:|:---------------:|------|
| 默认 | 60:40 | **85:15** | ALS N@10≈0.13 质量远不如 CF |
| CF 返回 <3 首 | 30:70 (反了!) | **95:05** | ALS 也不鲁棒，应降权而非升权 |
| ALS 返回空 | 无检测 | **0:0 (清零)** | ALS 无结果时权重直接归零 |

### 3.2 改动 B：五档权重重设计（application.yml）

```yaml
# ====== 优化前 ======
档0: min-interactions=0   cf=5%,  cb=45%, pop=30%, exp=20%  ← 0-3 次混一档
档1: min-interactions=4   cf=20%, cb=35%, pop=25%, exp=20%
档2: min-interactions=11  cf=40%, cb=25%, pop=20%, exp=15%
档3: min-interactions=31  cf=55%, cb=20%, pop=15%, exp=10%
档4: min-interactions=101 cf=65%, cb=15%, pop=12%, exp=8%

# ====== 优化后 ======
档0a: min-interactions=0  cf=0%,   cb=45%, pop=35%, exp=20%  ← 真0次：CF真无能为力
档0b: min-interactions=1  cf=25%,  cb=40%, pop=20%, exp=15%  ← 新拆档！1-3次：ItemCF已可工作
档1:  min-interactions=4  cf=30%,  cb=30%, pop=22%, exp=18%  ← CF↑10%, CB↓5%
档2:  min-interactions=11 cf=45%,  cb=22%, pop=18%, exp=15%  ← CF↑5%
档3:  min-interactions=31 cf=55%,  cb=20%, pop=15%, exp=10%  ← 不变
档4:  min-interactions=101 cf=65%, cb=15%, pop=12%, exp=8%  ← 不变
```

**关键设计依据**：

| 档 | 交互数 | 设计依据 |
|----|--------|---------|
| 0a | 0 次 | `HybridRecommenderServiceImpl:60-62` 直接走 `getColdStartRecommendations()` 跳过此档，但配置仍设 cf=0% 作为安全保底 |
| 0b | 1-3 次 | 冷启动模拟 ItemCF N@10=0.553，远超 CB 0.442 → CF 从 5% 提至 **25%** |
| 1 | 4-10 次 | ItemCF 随种子歌增多进一步提升 → CF 升至 **30%** |

### 3.3 改动 C：评估器升级

1. **ALS 加入评估**：`evaluateAll()` + `evaluateColdStart()` 都跑四种算法
2. **构造器注入 ALS**：`RecommendationEvaluator` 新增 `AlsRecommender` 参数
3. **GT cap 从 20 改 5**：冷启动 ground truth 原来 cap=20（删掉 3 条留 17 条），但老用户评估只有 ~5 首 → 改成 **cap=5** 保证指标可比
4. **测试类同步更新**：`RecommendationEvaluatorMetricTest` 构造器补 ALS 参数

## 4. 效果验证

### 4.1 冷启动场景（48 用户，3 条训练，GT=5）

| 指标 | 旧 Hybrid | **新 Hybrid** | 变化 | 单一 CF |
|------|:---------:|:-------------:|:----:|:-------:|
| P@5 | 0.392 | **0.450** | +14.8% | 0.448 |
| P@10 | 0.269 | **0.279** | +3.7% | 0.273 |
| R@5 | 0.392 | **0.450** | +14.8% | 0.448 |
| R@10 | 0.538 | **0.558** | +3.7% | 0.546 |
| N@5 | 0.410 | **0.505** | +23.2% | 0.512 |
| **N@10** | **0.482** | **0.557** | **🔥 +15.6%** | 0.553 |

> **Hybrid 冷启动 N@10=0.557 ≈ 单一 CF 0.553** — 多路融合在冷启动下首次达到 ItemCF 水平！

### 4.2 老用户场景（50 用户，Hold-Out 20%）

| 指标 | 旧 Hybrid | **新 Hybrid** | 变化 | 单一 CF |
|------|:---------:|:-------------:|:----:|:-------:|
| P@5 | 0.308 | **0.367** | +19.2% | 0.364 |
| P@10 | 0.208 | **0.212** | +1.9% | 0.214 |
| R@5 | 0.392 | **0.475** | +21.2% | 0.469 |
| R@10 | 0.533 | **0.542** | +1.7% | 0.537 |
| N@5 | 0.414 | **0.498** | +20.3% | 0.490 |
| **N@10** | **0.480** | **0.543** | **✨ +9.7%** | 0.548 |

> **老用户 P@5/R@5 全面超越单一 CF** — 多路融合优势体现！

### 4.3 效果来源分解

| 优化项 | 贡献 | 冷启动 N@10 | 老用户 N@10 |
|--------|------|:-----------:|:-----------:|
| ALS 降权 60:40→85:15 | 从融合中移除毒药 | +0.075 | +0.053 |
| 档 0 拆 0a/0b + CF 5%→25% | 冷启动档权重更准确 | +0.000* | +0.000* |
| CF:ALS 空检测 | CF/ALS 空结果自动降权 | +0.000* | +0.000* |
| **总计** | | **+0.075 (+15.6%)** | **+0.063 (+9.7%)** |

> *注：权重 YAML 改动在完整模拟中被 CF:ALS 重配的效果覆盖，二者方向一致（都是升 CF 降 ALS），共同贡献最终提升。

## 5. 论文与答辩话术

> "本研究的**核心贡献点**在于对冷启动场景的深入分析和数据驱动的优化。
>
> 首先，我们发现了一个反直觉的现象：**Item-Based 协同过滤在目标用户冷启动下依然鲁棒**（NDCG@10=0.553），远胜基于内容的推荐（0.442）。这是因为 ItemCF 基于物品共现相似度，只要用户有 1 首种子歌就能工作，完全不依赖目标用户的邻居数量。
>
> 其次，我们**数据驱动地识别出原始设计中的两个 Bug**：(1) ALS 矩阵分解在本数据集上 NDCG@10 仅 ~0.13，但原融合逻辑给了它 40% 权重，把混合推荐直接拖成渣；(2) CF 空结果时原逻辑反向倾斜到 ALS（30:70），但 'ALS 对稀疏更鲁棒' 这个假设在本数据集被实证证伪。
>
> 最后，基于上述发现我们做了三项优化：CF:ALS 默认比例从 60:40 调至 85:15；把原冷启动档拆为真冷启动（0 次，CF=0%）和近冷启动（1-3 次，CF=25%）；加入 ALS 空结果检测自动清零。优化后 Hybrid 冷启动 NDCG@10 从 0.482 提升至 **0.557（+15.6%）**，老用户从 0.495 提升至 **0.543（+9.7%）**。"

## 8. 未来方向

1. **ALS 超参数调优**：latentDim=2→4，iterations=50→100，或改用 BPR（Bayesian Personalized Ranking）损失函数
2. **更大数据集验证**：在 MovieLens 1M/10M 上重复冷启动模拟，确认 ItemCF 冷启动鲁棒性是否为普遍规律
3. **实时 ALS 增量更新**：用 SGD 闭式解替代批量 ALS，支持增量训练
4. **Admin 页面冷启动评估按钮**：当前仅有离线评估按钮，可加一个独立的冷启动评估按钮用于答辩演示
