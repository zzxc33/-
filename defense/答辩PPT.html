Chapter 01 · 课题背景与研究意义

为什么需要这个系统？

💡 问题：信息过载

全球在线音乐订阅用户突破 5 亿，曲库规模 数千万首。
传统排行榜 → 反映热门但无法个性化；
关键词搜索 → 需要用户明确意图；
推荐系统 在"不知道自己想听什么"时主动推送。

🎯 为什么我们做？

学术缺口：论文多聚焦算法精度，缺少完整工程实践；
毕设缺口：多数只做算法原型，无完整业务闭环；
工业缺口：单一算法各有缺陷，混合策略是必由之路。

📊 三大核心创新点

Innovation #1
动态权重混合引擎
根据用户交互数自动调整 CF/CB/热门/随机 四者权重，解决冷启动
Innovation #2
双端统一后端
Thymeleaf Web + 微信小程序原生，共用同一套 Spring Boot REST API
Innovation #3
推荐引擎诊断后台
实时查看三算法独立推荐结果 + 权重可视化 + Cold Start 识别

Chapter 04 · 核心创新

动态权重融合策略

权重根据用户 interactionCount（交互记录数）自动调整，解决冷启动问题。 权重表定义在 HybridRecommenderService.java:55-67

❄️ 冷启动（0 条）
热门兜底 50%
随机探索 50%
COLD
稀疏（≤5 条）
CF 20%
CB 50%
热门 20%
随机 10%
SPARSE
🔥 活跃（>5 条）
CF 50%
CB 20%
热门 15%
随机 15%
NORMAL

🧮 融合公式

// HybridRecommenderService.java:77-84
long interactionCount = repo.countByUserId(userId);
if (interactionCount == 0) {
  return hotSongs + randomFill;  // 纯热门兜底
}
double cfW, cbW, popW, randW;
if (interactionCount <= 5) {     // 稀疏
  cfW=0.20; cbW=0.50; popW=0.20; randW=0.10;
} else {                          // 活跃
  cfW=0.50; cbW=0.20; popW=0.15; randW=0.15;
}
return cfW*CF_score + cbW*CB_score + popW*pop + randW*random;

🛡️ 降级与兜底逻辑

CF 和 CB 得分先做 min-max 归一化 到 [0, 1] 再加权；
如果 CF 和 CB 都返回空列表 → 降级为 热门 + 随机；
随机探索的目的：避免只推热门，增加多样性。

Cold Start
0 交互
热门 + 随机各 50%
Fallback
算法返回空
热门 Top N 自动填充
